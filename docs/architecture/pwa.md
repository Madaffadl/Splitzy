**[IMPLEMENTED]** Name and description are pulled from the same dictionary the page metadata uses,

No `screenshots`, no `shortcuts`, no `share_target`, no `protocol_handlers`, no
`display_override`. **[IMPLEMENTED]**

| File | Declared `sizes` | Real dimensions | `purpose` | Bytes | Used by |
|---|---|---|---|---|---|

| `/icon-512.png` | `512x512` | 512 × 512 ✅ | `any` | 185 KB | Splash screen, high-DPI launcher |
| `/icon-maskable-512.png` | `512x512` | 512 × 512 ✅ | `maskable` | 134 KB | Adaptive Android icon |
| `/apple-touch-icon.png` | — | 180 × 180 ✅ | — | 27 KB | iOS home screen, via `metadata.icons.apple` |

All four are square and all are under the 300 KB budget the test enforces. Verified with `sips`.

**[IMPLEMENTED]** `/logo.png` is **1920 × 2194 (portrait, 2.26 MB)** and is used only for in-app
rendering (`components/ui/Logo.tsx`) and as the `ImageObject` in the Organization JSON-LD. It is
never referenced as an icon, and `PWA_ICONS.md` states the rule explicitly.

### 2.1 The two defects this replaced

Both are documented in `manifest.ts`, `sw.js` and `manifest-icons.test.ts`, and both are historical
— **fixed**, with regression tests.

| Defect | Expected | Actual | Root cause | Evidence |
|---|---|---|---|---|
| Android install died silently | Tapping install produces an installed app | Chrome offered the prompt, then Google's WebAPK build server rejected the icon and the install failed with no error surfaced anywhere | `/logo.png` was declared `512x512` but is really `1920x2194`, and 2.26 MB — a timeout risk on Indonesian mobile data on top of being the wrong shape | [manifest-icons.test.ts](../../src/app/manifest-icons.test.ts) |
| Maskable icon cropped | Adaptive icon shows the full mark | Android masks to a circle of 80 % diameter, cutting the top and bottom off an edge-to-edge logo | A `maskable` icon needs its own **padded** asset; the same file was serving both purposes | `manifest.ts` comment |

**Recommendation (already applied):** dedicated square PNGs at their declared sizes, a separate
maskable variant scaled to 410/512 and padded with the source background, and a test that reads real
pixel dimensions from each PNG's IHDR chunk.

### 2.2 Regression tests **[IMPLEMENTED]**

[src/app/manifest-icons.test.ts](../../src/app/manifest-icons.test.ts) asserts, for every icon the
manifest declares:

1. The file exists in `public/` and begins with the PNG signature.
2. Its **real** IHDR dimensions equal the declared `sizes` string.
3. It is square.
4. It is `< 300_000` bytes.
5. A `maskable` icon exists and shares no `src` with any `any` icon.
6. A 192 px icon exists for the Android launcher.

Plus a second suite that parses `APP_SHELL` out of `sw.js` by regex and asserts every static asset
in it exists on disk.

The test file's own framing is the clearest statement of why it exists: *"Neither was catchable by
type-checking, linting or a build… Both bugs lived in the gap between what the code declared and
what was actually on disk."*

## 3. Service worker **[IMPLEMENTED]**

File: [public/sw.js](../../public/sw.js) — hand-written, no Workbox, no `next-pwa`.
Registered by [RegisterServiceWorker](../../src/components/providers/RegisterServiceWorker.tsx),
mounted once in the root layout.

Registration guards:

```ts
if (!("serviceWorker" in navigator)) return;
if (process.env.NODE_ENV !== "production") return;   // avoid stale-cache surprises while editing
```

Registration is deferred to the `load` event (or fires immediately if the document is already
complete), and errors are swallowed — registration may fail on insecure origins or old browsers.

### 3.1 Caching strategies

`CACHE_VERSION = "splitzy-v2"`. Bumping it invalidates old caches on deploy.

| Request | Strategy |
|---|---|
| Non-`GET` | **Not handled** — never cached, always network |
| Cross-origin (Supabase, Gemini, PostHog…) | **Pass through**, untouched |
| `/api/*` | **Pass through** — API responses are never cached |
| `request.mode === "navigate"` | **Network-first**, put a clone in cache, fall back to the cached response and then to the cached `/` |
| Everything else same-origin (`_next/static`, icons, manifest) | **Stale-while-revalidate** — serve cache immediately, refresh in the background, and fall back to cache if the network fails |

Lifecycle: `install` precaches `APP_SHELL` then `self.skipWaiting()`; `activate` deletes every cache
key that is not `CACHE_VERSION` then `self.clients.claim()`.

### 3.2 The precache defect **[IMPLEMENTED]** — fixed

| | |
|---|---|
| **Expected** | The app shell is precached so the offline fallback has something to serve |
| **Actual** | The cache was **completely empty**, and had been since day one |
| **Root cause** | `APP_SHELL` listed `"/icon.svg"`, a file that has never existed. `cache.addAll()` is **atomic**, so one 404 rejected the whole batch — and the trailing `.catch(() => {})` swallowed the rejection |
| **Evidence** | The comment block in [public/sw.js](../../public/sw.js) |
| **Fix (applied)** | `APP_SHELL = ["/", "/manifest.webmanifest", "/icon-192.png"]`, added individually via `Promise.allSettled(APP_SHELL.map(url => cache.add(url)))`, so one bad entry can no longer take the rest down. Guarded by the precache test in §2.2 |

### 3.3 Offline behaviour **[IMPLEMENTED]**

- A navigation while offline falls back to the cached page, then to the cached `/`.
- Static assets are served from cache.
- **There is no dedicated offline page** (no `/offline` route, no `offline.html`).
- API calls fail normally. The application layer, not the service worker, handles offline: the
  scan flow checks `navigator.onLine` up front, `useTravelData` tracks online state and drains the
  outbox on reconnect, and the editors keep working from `localStorage`.

**[INFERRED]** The offline story is deliberately owned by the app rather than the service worker,
which fits a local-first product: the tool pages need no network at all once loaded.

## 4. Install prompt — a deliberate non-implementation **[IMPLEMENTED]**

This is the most notable PWA decision in the codebase, and it is easy to misread as a missing
feature.

[PwaInstallTelemetry](../../src/components/providers/PwaInstallTelemetry.tsx) listens for
`beforeinstallprompt` **passively**:

```ts
const onBeforeInstallPrompt = (event: Event) => {
  const platforms = (event as Event & { platforms?: string[] }).platforms;
  capture(EVENTS.installPromptAvailable, { platforms: platforms ?? null });
};
```

**It does not call `preventDefault()`, does not stash the event, and never calls `prompt()`.**
The reasoning, quoted from the source:

> *IMPORTANT: this deliberately does NOT call preventDefault() on beforeinstallprompt. Doing so
> suppresses Chrome's own install UI and hands us the responsibility of surfacing our own — and if
> that UI is ever missing or buggy we would remove installs rather than add them. Listening
> passively leaves browser behaviour exactly as it is today. The cost is `userChoice`, which only
> resolves reliably when we call prompt() ourselves; accepted-vs-dismissed is not worth taking that
> risk for until the data says otherwise.*

Consequences:

- **There is no in-app install CTA or button anywhere.** Grep confirms no `prompt()` call and no
  install UI component.
- Chrome's native install affordance (omnibox icon / browser menu) is left fully intact.
- The `userChoice` outcome is unmeasurable, by choice.

### 4.1 What *is* measured

| Event | Fires when | Platform |
|---|---|---|
| `pwa_install_prompt_available` | Chrome judges the site installable | Android / desktop Chromium |
| `pwa_app_installed` | An install completes, from Chrome's prompt **or** the browser menu | Android / desktop Chromium |
| `pwa_launched_standalone` | Document load in standalone display mode | **All**, including iOS |

Standalone detection covers both platforms:

```ts
const standalone =
  window.matchMedia?.("(display-mode: standalone)").matches ||        // Android + desktop
  (window.navigator as Navigator & { standalone?: boolean }).standalone === true;  // iOS only
```

**[IMPLEMENTED]** The root layout mounts this once per document load, so `pwa_launched_standalone`
counts *launches*, not SPA navigations.

**[IMPLEMENTED]** The stated purpose is a health check, not a growth metric: *"A healthy gap between
those is normal (most people decline). A gap of 100 % over a meaningful sample means the install
path is broken again."* — the direct lesson of the icon defect, which went undetected for an unknown
number of months and was only found because someone tried it on their own phone.

**[IMPLEMENTED]** All three events depend on PostHog being configured. With
`NEXT_PUBLIC_POSTHOG_KEY` unset, the install funnel is unobserved.

## 5. iOS support **[IMPLEMENTED]**

iOS has no install prompt at all — the user adds the site from the Share sheet. The root layout
therefore sets:

```ts
appleWebApp: {
  capable: true,             // full-screen launch instead of a Safari tab
  title: "Splitzy",          // home-screen label, not the full SEO title
  statusBarStyle: "default",
},
icons: { icon: "/icon-192.png", apple: "/apple-touch-icon.png" },
```

The layout comment notes that iOS 15.4+ reads `display`/`short_name` from the manifest, but these
tags are the only thing older versions honour — and that `apple-touch-icon` is 180 × 180 because
that is the size Safari asks for. It was previously a **1.5 MB 2048 × 2048 JPEG downloaded in full by
every iPhone**.

`appinstalled` and `beforeinstallprompt` never fire on iOS, so `pwa_launched_standalone` is the only
evidence an iOS install ever happened.

**[VISUAL-VERIFIED]** Every criterion under the application's control is met. The only unknown is

### 10.2 `beforeinstallprompt` — behaves exactly as designed

**Expected** The event fires, Splitzy observes it **passively**, and Chrome's own install UI is left
intact.
**Actual** Confirmed by code path and by the absence of any install UI in 38 rendered captures —
there is no in-app install button anywhere, which is the intended outcome.
**Root cause** n/a — working as specified.

**[IMPLEMENTED]** Note that the headless harness cannot make Chrome *fire* `beforeinstallprompt`
(it requires the engagement heuristic and a real profile), so the listener itself was not observed
firing. What was verified is the consequence: no custom install affordance exists to interfere with
the browser's.

### 10.3 Service worker registration — a real limitation of the audit

**Expected** The SW registers on `load` in production.
**Actual** **Not observable in this harness.** Registration is guarded by
`process.env.NODE_ENV !== "production"`, which is satisfied by `next start` — but Playwright's
default context starts with a clean profile and the SW's effects (precache, offline fallback) only
manifest on a second visit.
**Root cause** n/a — testing limitation, not a defect.
**Recommendation** Add a Playwright test that navigates twice, then asserts
`navigator.serviceWorker.controller !== null` and that a subsequent offline navigation still renders.
See TC-PWA-003.

### 10.4 Offline behaviour — partially verified

| Scenario | Result |
|---|---|
| Static assets cached stale-while-revalidate | **[IMPLEMENTED]** — code path confirmed, not exercised |
| Navigation network-first with cached-shell fallback | **[IMPLEMENTED]** — not exercised |
| `/api/*` passed through, never cached | **[IMPLEMENTED]** — explicit early return in `sw.js` |
| Scan blocked before the request when offline | **[VISUAL-VERIFIED]** — the `navigator.onLine` pre-check is in the render path |
| **Dedicated offline page** | ❌ **absent** — navigation falls back to the cached `/` |

**Expected** A user offline on `/history` sees something meaningful.
**Actual** They receive the cached landing page, or nothing if `/` was never cached.
**Root cause** `APP_SHELL` precaches `/`, `/manifest.webmanifest` and `/icon-192.png` only; the
fetch handler's final fallback is `caches.match("/")`.
**Evidence** [public/sw.js](../../public/sw.js)
**Recommendation** Add an `/offline` route to `APP_SHELL` and fall back to it, so the user is told
they are offline rather than being silently returned to the marketing page.

### 10.7 Two findings the rendering pass added

**Finding A — the manifest is English-only regardless of locale.**
**Expected** An Indonesian visitor installing from `/id` gets an Indonesian app name and
description.
**Actual** They get English. `manifest.ts` reads `DEFAULT_LOCALE` unconditionally.
**Root cause** Chrome fetches one manifest per scope, so a per-locale manifest would need a
different `scope` or a dynamic `manifest.webmanifest` — the latter would make the route dynamic.
**Evidence** [app/manifest.ts](../../src/app/manifest.ts)
**Recommendation** Accept, or serve a locale-aware manifest link from the `/id` tree. Low priority —
the installed name is `short_name: "Splitzy"`, which is language-neutral.

**Finding B — the service-worker navigation cache retains authenticated pages.**
**Expected** Signing out removes locally cached personal data.
**Actual** `signOut()` clears seven `localStorage` keys but **not** the Cache Storage entries the SW
wrote for `/dashboard`, `/history` and `/history/[id]` — all of which the navigation handler caches
on first visit.
**Root cause** The `fetch` handler caches every successful same-origin navigation, with no
allowlist.
**Evidence** [public/sw.js](../../public/sw.js), [useAuth.ts](../../src/hooks/useAuth.ts)
**Recommendation** Either skip caching for authenticated routes, or call `caches.delete()` on
sign-out. Relevant on shared devices — the same threat model the `localStorage` purge already
addresses, left half-covered.
